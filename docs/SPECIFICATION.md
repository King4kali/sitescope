# SiteScope — Technical Specification v1.0

**Название:** SiteScope  
**Категория:** Website Audit & Monitoring SaaS  
**Назначение:** Full-Stack portfolio project с возможностью дальнейшего коммерческого развития.  
**Основной язык интерфейса:** английский, с архитектурной поддержкой локализации.  
**Статус:** техническое задание для разработки.

---

## 1.1. Назначение системы

SiteScope предоставляет возможность провести автоматический технический аудит публичного веб-сайта без установки программного обеспечения на компьютер пользователя.

Пользователь вводит URL, например `https://example.com`, запускает проверку и получает сохранённый отчёт.

Система должна:

- Получать содержимое публичной страницы.
- Анализировать HTTP-ответы и перенаправления.
- Проверять HTML-структуру и SEO-метаданные.
- Измерять производительность на мобильных и десктопных устройствах.
- Обнаруживать неработающие ссылки.
- Создавать скриншоты страницы.
- Проверять SSL/TLS и основные защитные HTTP-заголовки.
- Формировать список обнаруженных проблем с рекомендациями.
- Сохранять историю аудитов.
- Экспортировать результаты в PDF.

SiteScope не должен позиционироваться как полноценный пентест, инструмент гарантированной SEO-оптимизации или средство сертификации доступности по WCAG.

## 1.2. Категории пользователей

**Гость**

- Просматривает главную страницу и описание возможностей.
- Регистрируется или входит в систему.
- Не получает доступ к чужим отчётам.

**Зарегистрированный пользователь**

- Создаёт проекты.
- Добавляет публичные сайты.
- Запускает проверки.
- Просматривает историю.
- Скачивает отчёты.
- Управляет своими проектами.

**Администратор**

- Просматривает состояние очередей и сервисов.
- Управляет пользователями и блокировками.
- Контролирует системные ограничения и ошибки.
- Просматривает технические метрики без доступа к чужим приватным данным сверх административной необходимости.

## 1.3. Основные пользовательские сценарии

**Сценарий A: первый аудит**

1. Пользователь проходит авторизацию.
2. Нажимает New Project.
3. Вводит название проекта и URL.
4. Нажимает Run Audit.
5. Сервер валидирует URL и права пользователя.
6. Создаётся задача в очереди.
7. Интерфейс отображает текущий этап выполнения.
8. Анализатор выполняет проверки.
9. Результаты сохраняются.
10. Пользователь открывает отчёт.

**Сценарий B: повторный аудит**

1. Пользователь открывает проект.
2. Нажимает Re-run Audit.
3. Запускается новый независимый аудит.
4. После завершения отображается сравнение с предыдущим запуском.

**Сценарий C: экспорт**

1. Пользователь открывает готовый отчёт.
2. Нажимает Export PDF.
3. Сервер создаёт PDF или возвращает готовый файл.
4. Пользователь получает документ с фактическими результатами проверки.

## 2. Функциональные требования

### FR-01. Регистрация и авторизация

Реализовать:

- Регистрацию через email и пароль.
- Подтверждение email.
- Авторизацию и выход.
- Восстановление пароля.
- Защищённые сессии.
- Изменение профиля.
- Удаление аккаунта с очисткой пользовательских данных по принятой политике хранения.

Пароли сохраняются исключительно в виде защищённых хешей Argon2id.

GitHub OAuth — дополнительная функция после MVP.

### FR-02. Управление проектами

Пользователь может:

- Создать проект.
- Указать публичный URL сайта.
- Изменить название.
- Просмотреть все аудиты.
- Повторить проверку.
- Удалить проект.

У каждого проекта имеется UUID, владелец и связанная история.

Один пользователь может добавить несколько проектов с разными URL.

### FR-03. Валидация URL

Разрешены только публичные HTTP/HTTPS-ресурсы.

Система должна отклонять:

- Некорректные URL.
- Адреса локальной сети.
- Loopback-адреса.
- Приватные IP и служебные диапазоны.
- Обращения к cloud metadata endpoints.
- URL с встроенными логином и паролем.
- Запрещённые порты и протоколы.
- Перенаправления в запрещённые сети.

В MVP разрешить порты 80/443, ограничить длину URL и запретить URL с пользовательскими учётными данными.

Проверки должны проводиться не только на входе, но и при DNS-разрешении, каждом перенаправлении и сетевом запросе браузера.

### FR-04. Система аудита

Один запуск создаёт отдельную запись Audit и набор результатов.

**Режим MVP:**

- Проверяется главная целевая страница.
- Выполняются мобильный и десктопный Lighthouse-аудиты.
- Для внутреннего SEO-обхода допускается до 5 HTML-страниц.
- Проверяется до 30 обнаруженных ссылок.
- Создаются два скриншота.
- Сохраняются все результаты и ошибки отдельных этапов.

Установить настраиваемые ограничения времени, числа запросов, объёма загрузок и числа редиректов.

### FR-05. Результаты и история

Для каждого аудита хранить:

- Исходный URL.
- Итоговый URL после редиректов.
- Время запуска и окончания.
- Статус.
- Успешность отдельных проверок.
- Оценки Lighthouse.
- Фактические измерения.
- Найденные проблемы.
- Скриншоты.
- Ссылку на PDF при его создании.
- Версии инструментов и профиль проверки.

Нельзя подменять неуспешную проверку нулевым или случайным значением.

### FR-06. Отчёты

Отчёт должен содержать:

1. Обзор состояния сайта.
2. Performance — mobile/desktop.
3. SEO.
4. Accessibility.
5. HTTP/TLS/Security Headers.
6. Broken Links.
7. Screenshots.
8. Issues and Recommendations.
9. Техническую информацию о запуске.

Каждая проблема включает название, серьёзность, описание, подтверждающие данные и возможное решение.

### FR-07. Экспорт PDF

PDF включает дату, проверенный URL, показатели, обнаруженные ошибки и рекомендации.

Если аудит частично выполнен, PDF должен явно указывать, какие проверки завершились ошибкой.

### FR-08. Пользовательские лимиты

В MVP задать конфигурируемые ограничения:

- До 3 проектов на пользователя.
- До 5 аудитов в сутки.
- Не более 1 активного аудита на пользователя.
- До 5 страниц внутреннего обхода.

Это стартовая политика для демоверсии, а не окончательная тарифная модель.

### FR-09. Панель администратора

Администратор должен видеть:

- Число зарегистрированных пользователей.
- Количество задач в очереди.
- Активные аудиты.
- Ошибки выполнения.
- Среднюю длительность задач.
- Загрузку воркеров.
- Объём хранилища.
- Состояние PostgreSQL и Redis.

## 3. Подсистемы проверки сайтов

| Модуль | Проверки |
|---|---|
| Performance | Lighthouse Performance, FCP, LCP, CLS, TBT, Speed Index |
| SEO | Title, description, H1, canonical, robots, sitemap, indexability |
| Links | Внутренние ссылки, редиректы, 4xx/5xx, некорректные адреса |
| Security | TLS-сертификат, HTTPS, HSTS, CSP, X-Content-Type-Options и другие заголовки |
| Accessibility | Автоматические Lighthouse/axe-core проверки, alt, имена кнопок, контраст и другие поддерживаемые правила |
| HTTP | Статус ответа, цепочка редиректов, время ответа, content-type |
| Visual | Скриншоты mobile и desktop |
| Field Data | Дополнительные реальные пользовательские метрики CrUX, если данные доступны |

**Performance:** первичными считаются результаты Lighthouse. Мобильная и десктопная проверки хранятся раздельно. INP не следует выдавать за автоматически измеренную метрику стандартного Lighthouse-аудита загрузки; реальные пользовательские данные получать отдельно через CrUX API.

**SEO:** система ищет технические проблемы, но не обещает позицию сайта в Google.

**Security:** проверка HTTP-заголовков и сертификата не означает, что сайт защищён от всех атак.

**Accessibility:** автоматическая проверка не подтверждает полное соответствие WCAG.

Для каждого модуля сохраняются `status`, `score` при наличии, `rawData`, `findings`, `errorCode` и `durationMs`.

### 5.3. Принцип обработки

API не должен выполнять тяжёлую браузерную проверку внутри HTTP-запроса.

При запуске аудита API сохраняет задание и передаёт его в BullMQ.

Независимый worker выполняет проверку, обновляет статус и сохраняет результаты.

Браузерная часть запускается в специально изолированной среде.

Базовый префикс: `/api/v1`.

Все пользовательские методы, кроме авторизации и публичной документации, требуют действующей сессии.

Использовать единый формат API-ошибок с `code`, `message`, `requestId` и необязательными `details`.

## 7. Очереди и воркеры

### 7.1. Redis и BullMQ

Предусмотреть очереди:

- `audits` — координация анализа.
- `browser-audits` — ресурсоёмкие браузерные проверки.
- `reports` — генерация PDF.

В MVP допускается одна очередь аудитов с последовательным выполнением этапов, но архитектура должна позволять отделить браузерные задачи.

### 7.2. Состояния

`QUEUED → RUNNING → COMPLETED`

Дополнительные исходы:

- `PARTIAL` — часть модулей не выполнилась.
- `FAILED` — аудит невозможно выполнить.
- `CANCELLED` — отменён до завершения.

### 7.3. Надёжность

- Redis сохраняет состояние очередей.
- PostgreSQL сохраняет итоговое бизнес-состояние.
- Job ID связывается с Audit ID.
- Повторная доставка не должна создавать дублирующиеся результаты.
- Использовать идемпотентность при постановке задания.
- Для предотвращения рассинхронизации БД и очереди использовать transactional outbox и периодическую сверку.
- Повторять только временные ошибки.
- Использовать backoff с ограниченным числом попыток.
- Фиксировать окончательные ошибки.
- После перезапуска восстанавливать незавершённую работу.

### 7.4. Ресурсные ограничения

Начальные настройки MVP:

- Один активный аудит на пользователя.
- Один активный обход конкретного hostname.
- Ограниченное число одновременно работающих Chromium-процессов.
- Пауза между запросами к одному сайту.
- Ограничения времени, памяти, количества страниц и скачиваемых данных.
- Реакция на HTTP 429 и 503 с замедлением и остановкой при необходимости.

Число browser workers выбирается по результатам нагрузочного тестирования.

## 8. Безопасность

Поскольку система принимает произвольные URL, сетевые проверки относятся к критически важной части архитектуры.

### 8.1. Защита от SSRF

Реализовать:

- Строгий разбор URL.
- Allowlist протоколов.
- Запрет локальных и специальных IP-диапазонов.
- Проверку IPv4/IPv6.
- Защиту от DNS rebinding.
- Проверку каждого перенаправления.
- Ограничение выходящих сетевых соединений средствами инфраструктуры.
- Запрет доступа браузера к приватной инфраструктуре.
- Ограничение портов.
- Защиту от бесконечных редиректов.

Одной проверки строки URL недостаточно.

### 8.2. Изоляция браузера

- Запускать Chromium вне основного API-процесса.
- Использовать отдельные изолированные runtime/container-окружения.
- Запускать процессы не от root.
- Сохранять sandbox Chromium.
- Ограничивать память и CPU.
- Не предоставлять браузеру доступ к секретам, внутренней сети и облачным метаданным.
- Удалять временные пользовательские данные браузера после выполнения.

Для публичного production-развёртывания браузерным процессам нужна отдельная сетевая изоляция и фильтрация исходящих соединений, а не только стандартный Docker-контейнер.

### 8.3. Безопасность приложения

- HTTPS.
- HttpOnly, Secure, SameSite cookies.
- CSRF-защита для cookie-аутентификации.
- Rate limiting.
- Валидация DTO через Zod/class-validator.
- Проверка владельца ресурса при каждом запросе.
- Защита административных endpoints.
- Секреты только на сервере.
- Ротация и ограничение API-ключей.
- Безопасная очистка логов от токенов.
- Приватные объекты в файловом хранилище.
- Короткоживущие подписанные ссылки для получения файлов.

### 8.4. Этичный обход

- Использовать идентифицируемый User-Agent.
- Соблюдать применимые правила robots.txt для автоматического обхода.
- Не обходить авторизацию, CAPTCHA и защитные механизмы.
- Не выполнять активный поиск уязвимостей.
- Не отправлять формы, выполняющие изменения.
- Не собирать закрытые данные.
- Не перегружать проверяемый сайт.

## 9. Нефункциональные требования

**Надёжность**

Сбой одного аналитического модуля не должен уничтожать результаты остальных.

**Производительность API**

Для обычных запросов без запуска браузера целевой p95 — до 300 мс при согласованной тестовой нагрузке. Это целевой показатель, а не заранее гарантируемое SLA.

**Длительность аудита**

Проверка выполняется асинхронно. Время зависит от сайта, браузера и доступных ресурсов. Задать конфигурируемый timeout для каждого этапа и всего задания.

**Масштабируемость**

API и воркеры должны масштабироваться независимо.

**Логирование**

Структурированные JSON-логи с request ID, audit ID и кодом ошибки.

**Наблюдаемость**

Метрики продолжительности задач, глубины очереди, использования ресурсов и частоты ошибок.

**Доступность интерфейса**

Адаптивная вёрстка, клавиатурная навигация, семантические элементы и корректные состояния загрузки.

**Резервное копирование**

Регулярный backup PostgreSQL, проверка восстановления, политика хранения файлов.

## 10. Тестирование и критерии приёмки

### Unit tests

Проверить нормализацию URL, вычисление результатов, правила SEO, ограничение тарифов и бизнес-логику.

### Integration tests

Проверить PostgreSQL, Prisma, Redis, BullMQ, механизм авторизации и постановку задач.

### End-to-end tests

Проверить регистрацию, создание проекта, запуск анализа, получение отчёта и экспорт PDF.

### Security tests

Проверить запрет loopback, приватных адресов, нестандартных портов, небезопасных перенаправлений, DNS rebinding и доступ к чужим проектам.

### Acceptance criteria

- Пользователь может зарегистрироваться и авторизоваться.
- Можно создать проект по `https://example.com`.
- Аудит создаётся как реальная фоновая задача.
- Результаты отражают фактические проверки.
- Ошибки отдельных модулей корректно отображаются.
- После обновления страницы сохраняются текущий статус и история.
- Lighthouse mobile/desktop результаты отображаются раздельно.
- PDF содержит данные именно выбранного аудита.
- Доступ к чужим проектам блокируется.
- После перезапуска сервисов данные сохраняются.
- Приложение запускается по документированной Docker-конфигурации.
- GitHub-репозиторий содержит тесты, документацию и инструкции.

## 11. Что не входит в первоначальный MVP

- AI-чат с анализом сайтов.
- Полный обход тысяч страниц.
- Массовая проверка доменов.
- Настоящий пентест.
- Проверка сайтов за авторизацией.
- Автоматическое исправление ошибок чужого сайта.
- Командная работа с ролями.
- Оплата подписки.
- Полноценная система уведомлений.
- Публичное API для сторонних клиентов.

Эти возможности добавляются после стабилизации основного анализатора.

## 12. Definition of Done

Версия 1.0 считается завершённой, когда пользователь способен самостоятельно зарегистрироваться, добавить публичный URL, запустить настоящий асинхронный аудит, увидеть измерения и обнаруженные проблемы, вернуться к сохранённому отчёту и скачать PDF.

Выполнение должно быть воспроизводимым, с понятными ошибками и без использования фиктивных данных.
